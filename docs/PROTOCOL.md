# Протокол Insta360 Luna Ultra

Заметки, взятые из `apatassini/Insta360luna` (MIT) и `RigacciOrg/insta360-wifi-api` (GPLv3),
сопоставленные с измерениями на аппарате. Полевые и командные числа используются как есть;
код приложения описывается ниже.

## Транспорт

TCP `192.168.42.1:6666`. Фрейминг **UCD2**, данные — **protobuf** (`insta360.messages`).

```
 0   4   'U' 'C' 'D' '2'      сигнатура
 4   1   0x01                 версия
 5   1   0x0c                 флаги
 6   1   тип                  0x01 медиа, 0x04 команда/ответ, 0x05 поток
 7   1   seq                  8-битный счётчик
 8   4   len (LE)             длина тела
12   len тела
     4   контрольная сумма (LE) контрольная сумма по данным от сигнатуры до тела
```

### Контрольная сумма

Нестандартный вариант CRC-32: полином `0x04C11DB7`, инициализация `−1`, и для каждого байта
XOR с **младшим** байтом, затем **четыре** прогона по таблице старшего байта. Это не
стандартный CRC-32, и его не стоит «чинить»: камера отбрасывает фреймы с неверной контрольной суммой.

### Открытие сессии

Команды входа не существует. Разрешение даётся отправкой фрейма **типа поток** (`0x05`) с
нулевой длиной и постоянным токеном `f6 cc 4f 09` вместо контрольной суммы; он повторяется каждые
**3 с** для поддержания связи. Сессия стабилизируется примерно через 1500 мс после первого фрейма.

Если соединение падает в течение 5000 мс после открытия, причина почти всегда в том, что у
камеры **одна управляющая сессия**: официальное приложение Insta360 нужно полностью закрыть.

### Команды

Тело фрейма команды начинается с 9 байт:

```
 0   2   code (LE)
 2   1   направление         0x02 запрос, 0x03 ответ
 3   2   requestId (LE)       именно он связывает запрос и ответ, а не seq
 5   4   0x00008000 (LE)      константа
 9   ..  сообщение protobuf
```

Важно учитывать три особенности поведения:

- ответ **не** повторяет код команды: он всегда равен `200`;
- камера **не** отправляет сообщения `Error`: на неизвестный код, некорректные данные и на
  настоящую команду без аргументов она отвечает одинаково — `200` с пустым телом;
- `TAKE_PICTURE` отвечает, когда **приняла** кадр, а не когда файл записан. Решение
  приходит в виде уведомления (8208 со статусом занято, либо 8201 с кодом ошибки).

### Коды

| код | команда |
|---|---|
| 3 | `TAKE_PICTURE` |
| 4 / 5 | `START_CAPTURE` / `STOP_CAPTURE` |
| 7 / 8 | `SET_OPTIONS` / `GET_OPTIONS` |
| 9 | `SET_PHOTOGRAPHY_OPTIONS` |
| 11 | `GET_FILE_EXTRA` |
| 12 | `DELETE_FILES` |
| 13 | `GET_FILE_LIST` |
| 15 | `GET_CURRENT_CAPTURE_STATUS` |
| 118 | `SET_ACCESS_CAMERA_FILE_STATE` (см. раздел «Гимбал»; эффект зависит от состояния/прошивки, нужен тест на устройстве) |
| 16 | `SET_FILE_EXTRA` (на этой прошивке ничего не делает) |
| 17 / 18 | `GET` / `SET_TIMELAPSE_OPTIONS` |
| 22 / 23 | `START` / `STOP_TIMELAPSE` |
| 30 | `GET_MINI_THUMBNAIL` (не реализовано) |

### Уведомления

| код | содержимое |
|---|---|
| 8195 | батарея (поле 2 уровень, поле 3 масштаб) |
| 8198 / 8199 | накопитель |
| 8201 | съёмка прервана: 1 карта полна, 2 занята, 4 карта медленная, 7 батарея, 9 температура |
| 8208 | статус съёмки: поле 1 статус, 2 время, 3 число кадров |
| 8220 | выдержка |
| `0x206A` | скорость гимбала |
| 8302 | PTZ (не подтверждён) |

Статусы съёмки: `4` = ведётся одиночный кадр, `15` = ведётся панорама, `0` = свободно.

### Гимбал

Камера выполняет `GIMBAL_CONTROL` (`0x00E2`) и `TAKE_PICTURE` **только при активном
 видеопотоке**. Если поток не активен, камера возвращает пустой ответ `200`, но не выполняет
 команду. Поэтому при подключении запускаются **оба** канала видеопотока:
- **TCP-поток** `START_LIVE_STREAM` (код 1) — **разрешает работу** гимбала и съёмки;
- **OSC-MJPEG** (HTTP `camera.getLivePreview`) — картинка для экрана, если камера его
  предлагает.

Если камера предлагает MJPEG, картинка идёт через него; если нет — через TCP-поток и
декодёр MediaCodec (H.265, Annex-B). TCP-поток при этом держится, чтобы команды оставались
доступны и во время съёмки.

`SET_ACCESS_CAMERA_FILE_STATE` (118, `AccessState.LIVE_VIEW=5`) — команда, эффект которой
пока подтверждён не полностью. В текущем приложении она отправляется без гарантии успеха перед
`START_LIVE_STREAM` при запуске и восстановлении прямого эфира; ошибка/таймаут этой команды
не блокирует отправку START. В `android/tools/Smoke.java` проверяется только кодирование полезной нагрузки в последовательность `08 05`
и числовой код 118, а не поведение камеры.

Изученные внешние референсы запускают прямой эфир без этой команды, но это само по себе не
доказывает, что команда всегда запрещена или что она ломает гимбал: поведение может зависеть
от версии прошивки и текущего состояния камеры. В исходниках приложения комментарии ранее
утверждали и обратное («нужна для разворота»), и запрет. Поэтому до контролируемого теста на
устройстве не считать её обязательной или безопасной во всех сценариях. Не отправлять её
перед каждым движением; её место сейчас — только последовательность запуска/восстановления.
Ответ `200` также не подтверждает, что прямой эфир действительно выдаёт кадры: клиент ждёт
первый кадр отдельно.

`GIMBAL_CONTROL` (`0x00E2`), поле 1 = действие, поле 2 = вложенное сообщение с осями в
зигзаге:

- `08 01 12 <len> <axes>` = `MOVE`; `12 00` (пустые оси) = **стоп**, отправляется 4 раза
  через 25 мс;
- вложенное поле 1 = `device_x` = **вертикально**, поле 2 = `device_y` = **горизонтально**,
  диапазон −100…100;
- действия без осей: 2 = вернуться в центр, 3 = переключить фронтальную камеру.

### Панорама

**Встроенный режим камеры в официальном приложении Insta360.** Приложение делает
360-панораму не склеиванием на телефоне, а встроенным режимом камеры: камера сама ведёт
гимбал по **19 позициям**, снимает и **выполняет сшивку внутри камеры**, сохраняя **один**
готовый 360-JPG (8000×4000). Оригиналы 19 кадров не сохраняются. Последовательность команд: `SET_OPTIONS`
`photo_sub_mode = PHOTO_INSTA_PANO (8)` → `SET_PHOTOGRAPHY_OPTIONS` `PANO_ASPECT (98) =
SPHERE_360 (1)` под `function_mode = NORMAL_POWER_PANO_IMAGE (14)` → **один**
`TAKE_PICTURE` с `isInstaPanoEnabled=true`. При этом приложение не двигает гимбал — гимбал
ведёт камера.

**24 кадра для внешней сшивки (PanoLuna).** Задача — 24 отдельных полных кадра для сшивки
на компьютере, сохранение **на камеру**. Поэтому используется другой режим:

1. `SET_OPTIONS` + `photo_sub_mode = PHOTO_SINGLE (0)` — обычный одиночный кадр (не
   INSTA_PANO: он нужен только для встроенной 19-кадровой сшивки).
2. Параметры фото до съёмки: `SET_PHOTOGRAPHY_OPTIONS` (разрешение `PHOTO_SIZE_ID`,
   выдержка, баланс белого, компенсация, яркость, зум, RAW).
3. Поворот гимбала по 24 точкам плана через `GIMBAL_CONTROL` (вектор скорости, `driveTo`
   к каждой точке). Гимбал должен быть неподвижен в момент съёмки.
4. Для каждой точки — обычный `TAKE_PICTURE` (без `isInstaPanoEnabled`), затем ожидание
   `GET_CURRENT_CAPTURE_STATUS` (статус `15` = ведётся захват, `0` = свободно): ответ
   `TAKE_PICTURE` — когда камера **приняла** кадр, а не когда записала файл. Снимки
   остаются **на камере**; `TakePictureResponse.photo.uri` — их путь.

## HTTP-интерфейс

- Файлы: `http://192.168.42.1<path>`, например
  `/storage_internal/DCIM/Camera01/IMG_…jpg`.
- Предпросмотр прямого эфира: два пути, как в официальном приложении Insta360:
  1. **OSC-MJPEG** (первый): `POST /osc/commands/execute` с
     `{"name":"camera.getLivePreview"}`, поток MJPEG, который читается как последовательность
     `FF D8 … FF D9` (разделители кадра, не Content-Length).
  2. **TCP-поток** (резервный вариант): при `START_LIVE_STREAM` камера передаёт кадры MEDIA по TCP
     (подпоток `0x20`, полезная нагрузка Annex-B, **H.265** на прошивке 1.0.288). Декодируется через
     `MediaCodec` на `SurfaceView`; кодек определяется динамически по NAL (SPS/VPS), декодер
     запускается только после ключевого кадра.
- `camera.listFiles` требует заголовок `X-XSRF-Protected: 1`.

## Сеть Wi-Fi

SSID с префиксом `Luna Ultra`, подсеть `192.168.42.`, шлюз `192.168.42.1`. У сети нет
интернета: сокет нужно привязывать к `Network` Wi-Fi и держать регистрацию сети через
`NetworkRequest`, иначе Android сбросит её, как только приложение выйдет на передний план.
