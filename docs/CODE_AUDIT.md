# Аудит исходного кода PanoLuna

Дата: 2026-11-23. Область: исходники Android-приложения, чистая логика плана/протокола,
README и документация протокола. Это статический аудит и проверки на JVM, не полевой тест
на камере.

## Итоги

### Исправлено: единая геометрия шага панорамирования и перекрытия

`PanoPlan.build()` распределяет столбцы по всему физическому ходу гимбала `−57°…+235°`:
шаг между соседними столбцами равен `(PAN_MAX_DEG - PAN_MIN_DEG) / (columns - 1)`. Для
плана 4×6 это 58,4°. Ранее `getPanStep()` и расчёт перекрытия использовали `360 / columns`,
что не описывало реальные координаты плана. Теперь оба вычисления используют ту же формулу,
что и генерация точек.

Для измеренного горизонтального поля зрения 77,7° шаг 58,4° даёт около 25% горизонтального
перекрытия. Результат ограничивается диапазоном 10–60%; поэтому это оценка, а не измерение
перекрытия реальных фотографий. Добавлены проверки шага 58,4° и ожидаемой оценки 25% в
`android/tools/Smoke.java`.

### Уточнено: команда 118 и предпросмотр в реальном времени

Код приложения отправляет `SET_ACCESS_CAMERA_FILE_STATE(LIVE_VIEW=5)` (код 118, полезные данные
`08 05`) без гарантии успеха перед `START_LIVE_STREAM` при запуске и восстановлении. Однако проверка на JVM
подтверждает только код и байты полезной нагрузки; внешние источники, запускающие поток без команды 118, не дают
достаточного основания объявлять команду всегда вредной или обязательной. Ранее исходный
комментарий и `docs/PROTOCOL.md` содержали взаимоисключающие безусловные утверждения.
Документация теперь отделяет подтверждённое поведение кода от неизвестной реакции прошивки.
Поведение команды требует контролируемого испытания на устройстве и конкретной версии
прошивки.

### Обновлена документация пользовательского поведения

README больше не утверждает, что в интерфейсе есть круговой джойстик или встроенный экспорт
готового проекта: текущий экран предоставляет управление автоматической съёмкой, а найденные
генераторы шаблонов используются вспомогательными утилитами и проверками на JVM, но не связаны
с функцией экспорта в интерфейсе. Также явно указано, что приложение не задаёт качество и
разрешение фото и что сетевое подтверждение само по себе не доказывает применение настройки.

## Проверенные свойства и границы уверенности

- `PanoPlan.shot24()` строит 24 точки в сетке 4×6, с чередованием направления строк; тесты
  проверяют границы панорамирования и последовательность точек/выходные шаблоны.
- Панорама управляет гимбалом по оценке положения. По документации класса Gimbal, камера не
  возвращает подтверждённые абсолютные координаты; фактическое смещение механики может
  расходиться с интеграцией скорости.
- `TAKE_PICTURE` и отдельное ожидание статуса захвата — разные этапы; сетевой ответ о принятии
  команды не равен окончанию записи файла.
- `android/test.sh` не проверяет пользовательский интерфейс Android, многопоточность на устройстве,
  сетевое поведение, успешную запись каждого файла или физическую точность углов.
- Проверка неиспользуемых строк ресурсов выявила множество строк, не имеющих прямой ссылки в
  Java/XML. Некоторые могут использоваться косвенно через списки ресурсов/локали, поэтому
  массовое удаление не выполнялось.
- Настройки приложения сохраняются локально. Никаких изменений в логике управления качеством
  фотографий не вносилось.

## Комментарии в исходниках

Обновлены описания ответственности `PanoLunaApp`, `CameraClient`, `CameraConnection`,
`Gimbal`, `PanoPlan`, `Messages` и `Settings`: комментарии теперь подчёркивают различие
между отправкой команды, получением подтверждения и подтверждённым эффектом, а также оценочный характер
позиции гимбала. Неактуальные описания настроек и дублирующий комментарий к
отправке вектора удалены.

## Проверка

Запуск `bash android/test.sh` прошёл успешно. В том числе подтверждены сериализация объявления предпросмотра
`08 05`, код команды 118, 24 точки плана, шаг 58,4°, оценка перекрытия 25%, выход за физические
границы отсутствует. Тесты генераторов шаблонов также прошли.
